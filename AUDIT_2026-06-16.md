Из 61 проверенного пункта подтверждено 58; 3 — «uncertain» (две с частично неверным механизмом, одна с неверным заявленным impact).

## Баги корректности

По убыванию severity.

### CRITICAL

**1. Пароли SMTP-аккаунтов — plaintext в БД и в ответе API**
`app/models/smtp_account.py:11` (колонка `String`), `app/api/smtp_accounts.py:13,22,31,41`. `SmtpAccountResponse(SmtpAccountCreate)` наследует поле `password`, `GET /smtp-accounts/` отдаёт его в открытом виде. Потребляется в открытом виде в `generic_smtp_service.py:45,50`.
*Влияние:* любой, кто читает файл SQLite (деплой по SFTP) или дёргает эндпоинт, забирает живые почтовые пароли. Дефект независим от заморозки портов — данные хранятся уже сейчас.
*Рекомендация:* шифровать пароль at-rest (или хранить ссылку на app-password); разнести read/create-схемы — `password` пометить write-only и НИКОГДА не возвращать на GET.

### HIGH

**2. AuthMiddleware логирует префикс секрета и каждый путь на WARNING**
`app/main.py:122` (путь каждого запроса) и `:140` (`Expected: {GLOBAL_PASSWORD[:4]}...`). `GLOBAL_PASSWORD` задан в проде → ветка активна.
*Влияние:* раскрытие 4 символов общего bearer-секрета в любой лог-агрегатор + помощь брутфорсу; зашумление логов.
*Рекомендация:* убрать любую часть креденшала из лога; снять или понизить до DEBUG лог пути.
*(`main.py:135` — это ветка отсутствующего заголовка, не третья утечка.)*

**3. `get_company_dossier` фабрикует досье из пустого корпуса без поискового провайдера**
`tavily_osint.py:12`, `search_service.py:30` (приоритет по умолчанию `['yandex','tavily']`), `:104` (`search_configured` → True даже без ключей), `osint_worker.py:143`. При отсутствии обоих ключей `search_web` возвращает `[]`, контекст пуст, LLM генерит валидный JSON «из ничего», guard на `osint_worker.py:143` его не отбраковывает → пустое/галлюцинированное досье кэшируется как реальное.
*Влияние:* генерация заземляется на сфабрикованных фактах. Тихо.
*Рекомендация:* `search_configured` должен требовать реально пригодного провайдера (проверка `TAVILY_API_KEY`), либо возвращать error-строку при нуле хитов, чтобы guard пропустил запись.

**4. `enrich_crm_data` в воркфлоу есть, но не запускается автоматически → пустой `osint_dossier` в генерации**
`orchestrator.py:391-398` (явно НЕ авто-запускается), `continue_workflow_after_review:418-419` (только generate_master + generate_emails), `workflow_registry.py:4`. Досье пишет только `enrich_crm_data` (`osint_worker.py:147`), а промпт письма имеет жёсткое требование по нему (`outreach_email_pipeline.py:258`). В авто-потоке start→review→continue письма идут с пустым досье; ничто это не сигнализирует.
*Влияние:* подрывается персонализация, ради которой построен весь пайплайн. «Генерация работает» зависит от того, что кто-то вручную запустил OSINT-шаг.
*Рекомендация:* авто-запускать `enrich_crm_data` между validate и generate (за флагом), либо гейтить generate / показывать UI-статус «OSINT не запущен».

**5. Apollo перехватывает рабочий Yandex+LLM-пайплайн при `APOLLO_API_KEY`**
`contacts_worker.py:70-73` (`if apollo_configured(): return try_find_contacts_via_apollo(...) or {"contacts":[]}` — НИКОГДА не падает в LLM-путь ниже, строки 75-101 мертвы при заданном ключе), `research_worker.py:28-32` (короткое замыкание на Apollo). Гейт — только env-ключ. `setup_gate.py:53-55,142` отдаёт `apollo_outreach_ready`, фронт рисует лейбл «Apollo» (`AiBizOsHumanUI.jsx:756,1903-1904`).
*Влияние:* один env-ключ молча подменяет всё RU-обнаружение контактов/компаний на Apollo («бесполезен в RU»), без fallback для find-contacts.
*Рекомендация:* при выпиливании Apollo удалить короткие замыкания + поле setup-gate + FE-лейбл, либо инвертировать в явный per-run opt-in.

**6. Режим OSINT по умолчанию «hardcore» делает raw-SMTP RCPT на порт 25 — в проде не исполним**
`osint_worker.py:158` (хардкод `mode='hardcore'`, кроме `api_only`), `hardcore_osint.py:203-232,214-215` (`smtplib.SMTP(timeout=3).connect(mx)` + RCPT на 25). *Рекомендация:* сделать `api_only` эффективным дефолтом, пока SMTP заморожен, либо гейтить SMTP-пробу за runtime-флагом доступности.

### MEDIUM

**11. Reply-путь никогда не использует SMTP-ротатор → всегда падает на единственный глобальный Yandex**
`reply_sender.py:210`, `email_provider.py:31` (`if db:`), `email_sender.py:115`. Reply-путь не передаёт `db=`, ветка ротатора пропускается, всегда уходит в Yandex-fallback, не инкрементит счётчики ротатора. Латентно сейчас (SMTP заморожен), активируется при разморозке.
*Рекомендация:* передавать `db=db` в `send_email_via_provider` из `send_one_reply_draft`.

**12. Нет кросс-путевого гварда конкурентности на ран**
`restart_background_jobs.py:12-50`, `runs.py:515-544,612-628`, `orchestrator.py:405-425`. Restart сериализуется только против других restart (in-process set); `/continue` и `/start` идут синхронно без общей блокировки. Проверка `status=='needs_review'` рейсит против фонового restart-потока. Оба пути мутируют те же step-строки/контакты.
*Рекомендация:* единый per-run lock (`is_restart_in_progress` → generic «run busy»), 409 при занятом ране.

**13. Импортёр AmoCRM коммитит на каждую строку (commit-в-цикле)**
`import_crm.py:82-121`, `contact_repo.py:48-49`. `create_contact` делает full COMMIT+REFRESH на каждую строку; DataFrame итерируется дважды (62 и 82). На SQLite — тысячи отдельных транзакций, повторный захват writer-lock, нет атомарной границы отката.
*Рекомендация:* bulk-вставка с `commit=False` (прецедент — `sync_run_companies_from_dicts`), один commit после цикла; слить два прохода `iterrows()`.
*(Замечание: `synchronous=NORMAL` в `db.py:27` — fsync не на каждую транзакцию, формулировка «fsync per row» слегка завышена, но писательная contention реальна.)*

**14. Run-card list: ~10-14 COUNT-запросов на ран, без пагинации (N+1 на гранулярности рана)**
`runs.py:116-119`, `run_display_service.py:685-709,409-459`. `GET /runs/project/{id}` без limit/offset; `enrich_run_for_card` фанит ~12 round-trip на каждый ран (включая UNION-подзапросы). На single-writer SQLite сериализуется против записей пайплайна.
*Рекомендация:* limit/offset + сгруппированные агрегаты `GROUP BY run_id` один раз на проект.

**15. POST /runs/start выполняет весь синхронный пайплайн в обработчике запроса**
`runs.py:605`, `orchestrator.py:383-402,198-272`. `run_workflow` идёт инлайн (до 50 раундов collect/find/validate с LLM/HTTP); restart-путь намеренно делает 202 + daemon-thread.
